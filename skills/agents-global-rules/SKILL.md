# 全局代理规则 (AGENTS.md)

本 Skill 规范了 AI 智能体在开发时的行为，包含全局规则以及项目开发约束，旨在通过严格的标准来降低开发错误率并保证代码质量。

## 1. 编码前先思考 (Think Before Coding)

**不要假设。不要隐瞒疑惑。明确权衡利弊。**

在实现之前：
- 显式声明你的假设。如果不确定，请提问。
- 如果存在多种解释，请展示它们——不要默默做出选择。
- 如果存在更简单的方法，请说出来。在合理时予以拒绝。
- 如果有事情不明确，请停下来。指明令人困惑的地方并提问。
- 在做出更改之前，提出一个简要的实现计划，并征求用户明确的确认。
- 开始开发前，询问用户是在当前分支上工作还是创建新分支。如果创建新分支，其名称必须以 `codex/` 开头；`codex/` 后面的英文单词必须与需求匹配，保持简明，最多包含五个单词，并用 `-` 连接。
- 在切换到 `codex/*` 分支之前，先切换到 `main` 或 `master`，拉取最新的远程更改，然后从更新后的基座创建或切换到 `codex/*` 分支。

## 2. 简单至上 (Simplicity First)

**用最少的代码解决问题。不要有任何推测性的代码。**

- 不要提供超出要求的特性。
- 不要为单次使用的代码做抽象。
- 不要引入未要求的“灵活性”或“可配置性”。
- 不要为不可能发生的场景编写错误处理。
- 如果你写了 200 行，但本可以用 50 行实现，请重写它。

### 避免不必要的抽象与包裹 (Avoid Unnecessary Abstraction and Wrapping)

上述规则也适用于局部控制流 and 类型处理：

- 不要为了让代码“看起来更干净”而提取仅使用一次的方法、函数、常量、局部闭包、类型别名或配置对象。
- 保持一次性逻辑在当前控制流中内联，除非它满足抽象规则：至少 3 处调用、有意义的类型化输入/输出，且能清晰降低读者的理解复杂度。
- 不要使用 IIFE（立即调用函数表达式）来包裹同步或异步逻辑，例如 `(async () => { ... })()`。
- 不要仅为了立即调用而定义临时函数或闭包，例如 `const run = async () => { ... }; run()`。
- 不要引入额外的函数包裹器、异步包裹器、任务包裹器或调度器来绕过 `await`、错误处理、类型问题或代码放置。
- 默认情况下不要引入 `setImmediate`、`setTimeout`、`queueMicrotask`、`Promise.resolve().then(...)` 或类似的调度机制。只有当业务流程显式要求延迟执行、并发隔离或生命周期切换时才使用它们。
- 不要使用类型断言来绕过类型问题，例如 `as Error`、`as SomeHandler` 或 `as any`。优先使用类型收窄、类型守卫、字面量联合类型、泛型约束和类型化查找映射。

问问自己：“资深工程师会觉得这过于复杂吗？”如果是，请简化。

## 3. 精准修改 (Surgical Changes)

**只触碰必须触碰的地方。只清理自己留下的烂摊子。**

编辑现有代码时：
- 做出能解决问题的最小修改，优先考虑最小的业务范围。
- 不要“改进”相邻的代码、注释或格式。
- 不要重构没有损坏的东西。
- 匹配现有风格，即使你有不同的做法。
- 如果你注意到不相关的废弃代码，提出来——不要直接删除它。

当你的修改产生孤立代码时：
- 清理由于你的修改而变得不再使用的 import、变量或函数。
- 除非被要求，否则不要清理先前已存在的废弃代码。

检验标准：修改的每一行代码都应能直接追溯到用户的需求。

## 4. 目标驱动执行 (Goal-Driven Execution)

**定义成功标准。循环直到验证通过。**

将任务转化为可验证的目标：
- “添加校验” → “为无效输入编写测试，然后使测试通过”
- “修复 Bug” → “编写一个能复现它的测试，然后使测试通过”
- “重构 X” → “确保重构前后的测试都能通过”

对于多步骤任务，声明一个简要的计划：
```
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
3. [步骤] → 验证: [检查项]
```

清晰的成功标准能让你自主循环验证。模糊的标准（如“使其工作”）则需要不断的澄清。

## 项目约束 (Project Constraints)

- 在进行任何修改之前，阅读相关的源文件。
- 仅通过包管理器命令添加依赖，绝不直接编辑依赖清单（manifest）或锁文件。
- 提交信息遵循 `commitlint` / `config-conventional` 规范。
- 创建 commit 或 pr 时，附加必填的 commit 归属尾注 `Codex <noreply@openai.com>`。
- 提交前检查 changesets。
- 提交前务必走 Code Review。
- 当必须使用非常规的变通方案（例如 `as any`）时，先提问。
- 使用 Node.js 编写临时脚本。
- 保持类型定义靠近其使用的地方。
- 在服务器控制器接口中，在校验 `query`、`body` 或 `params` 之后，在业务逻辑执行前将实际使用的字段进行解构；避免在整个方法中重复访问 `body.xxx`、`query.xxx` 或 `params.xxx`。

### 抽象 / 重构策略 (Abstraction / Refactor Policy)

- 不要仅仅因为代码重复就提取辅助函数或常量。
- 仅在以下所有条件均满足时，才引入新的辅助函数：
  1. 相同的逻辑在 3 处或更多地方出现。
  2. 输入和输出是自然类型化的且有意义。
  3. 该抽象降低了读者的复杂度，而不是增加了复杂度。
- 宁可重复，也不要错误的抽象。
- 在引入新的辅助函数之前，先搜索已有的辅助函数。
- 始终使用中文沟通、制定计划、反馈 Code Review。
- 拒绝过度抽象：绝不提取仅使用一次的方法或变量。
- 在合适的地方优先使用箭头函数；避免使用 `function() {}`，除非需要真正的函数绑定（this 绑定）。
