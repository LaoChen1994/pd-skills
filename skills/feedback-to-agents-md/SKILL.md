# 反馈沉淀到 AGENTS.md

## 目标

当用户否定、纠正、批评 agent 的回答或执行方式时，不要只是继续完成当前任务，而是先判断这次反馈是否包含可复用规则。

如果反馈具有长期价值，应当：

1. 用中文总结这次问题。
2. 提炼出可复用规则。
3. 判断这条规则适合写入哪个 `AGENTS.md`。
4. 展示拟写入内容。
5. 等用户明确确认后，再修改文件。

所有与用户的沟通必须使用中文。

---

## 触发场景

当用户说出类似下面的话时，使用本 Skill：

* 不对
* 不是这个意思
* 你理解错了
* 你又犯了同样的问题
* 下次不要这样
* 以后记住
* 这个要写进 AGENTS.md
* 把这个规则沉淀下来
* 你应该总结一下
* 这不是我要的
* 你先别继续，先总结问题

---

## 不触发场景

以下情况不要写入 `AGENTS.md`：

* 只是一次性的任务修改。
* 只是当前文件、当前需求的临时要求。
* 用户没有表达“以后也要这样”的意思。
* 反馈中包含敏感、隐私、临时信息。
* 规则过于模糊，无法形成明确行为约束。

例如：

* “这个按钮改成蓝色”通常不要沉淀。
* “这次文案短一点”通常不要沉淀。
* “以后给我设计稿时，先给交互流程，再给视觉方案”可以沉淀。
* “以后不要直接重写整个文件，先说明最小修改范围”可以沉淀。

---

## 处理流程

### 第一步：停止盲目继续

当用户否定 agent 时，不要立刻继续执行原任务。

先用中文回应：

```md
我先暂停一下，先把这次反馈总结清楚，避免继续沿着错误方向做。
```

然后开始分析。

---

### 第二步：总结用户反馈

用中文总结三件事：

1. agent 刚才哪里做错了。
2. 用户真正想要的是什么。
3. 这是否是可复用规则。

输出格式：

```md
我理解这次反馈是：

- 我刚才的问题：
- 你真正想要的是：
- 是否适合沉淀为长期规则：
```

---

### 第三步：分类反馈类型

将反馈分类为以下之一：

* `global_preference`：用户长期偏好，适合写入全局 `~/.codex/AGENTS.md`
* `repo_rule`：当前项目规则，适合写入当前仓库的 `AGENTS.md`
* `workflow_rule`：某类重复工作流程规则，适合写入当前仓库或全局规则
* `style_rule`：写作、设计、回答风格规则
* `one_off`：一次性反馈，不写入

如果是 `one_off`，只总结，不修改文件。

---

### 第四步：提炼规则

把用户反馈改写成明确、短小、可执行的规则。

好的规则示例：

```md
- 当用户否定当前方向时，先暂停执行，总结误解点和新的执行方向，再继续。
- 修改已有代码时，优先给出最小 diff，不要默认大范围重写。
- 做官网引流获客方案时，优先给出可落地的页面形态、SEO 关键词和转化路径，而不是泛泛列 AI 工具。
- 设计类任务中，先给交互流程和信息结构，再给视觉表现建议。
- 当用户要求生成图片文案时，避免使用审核敏感词，并主动替换为更安全的表达。
```

不好的规则示例：

```md
- 用户不满意。
- 以后做得更好。
- 记住这次对话。
- 不要错。
```

---

### 第五步：让用户确认

在修改任何文件之前，必须先让用户确认。

输出格式必须是中文：

````md
我建议把这次反馈沉淀为下面这条规则：

> [规则内容]

建议写入位置：

- 文件：[AGENTS.md 路径]
- 章节：[章节名]

拟写入内容：

```md
[具体 Markdown 内容]
```

确认后我再写入。你可以回复「确认写入」「调整一下」或「不要写入」。
````

没有用户明确确认，不允许修改 `AGENTS.md`。

---

## 确认条件

只有当用户明确表达同意时，才可以写入文件。

可以视为确认的表达：

- 确认
- 确认写入
- 可以
- 写进去
- 更新
- 加进去
- OK
- yes

不能视为确认的表达：

- 嗯
- 继续
- 你看着办
- 应该可以
- 先这样

对于不明确表达，要继续用中文确认。

---

## 写入 AGENTS.md 的规则

修改 `AGENTS.md` 时，必须遵守：

1. 优先合并到已有相关章节。
2. 不要盲目追加重复规则。
3. 不要写入聊天细节，只写通用行为规则。
4. 每条规则要短、明确、可执行。
5. 避免写入隐私、账号、个人身份、临时任务信息。
6. If 已有规则冲突，先向用户说明冲突点，再让用户决定。

---

## 推荐章节

如果 `AGENTS.md` 中没有合适章节，可以新增：

```md
## Agent 反馈沉淀规则

- 当用户否定当前方向时，先暂停执行，总结误解点、用户真实意图和新的执行方向，再继续。
```

如果是设计类偏好，可以写入：

```md
## 设计任务偏好

- 设计类任务中，优先先给信息结构、交互流程 and 页面模块，再给视觉风格建议。
```

如果是代码类偏好，可以写入：

```md
## 代码修改偏好

- 修改已有代码时，优先采用最小修改，不要默认大范围重构。
```

如果是内容方案类偏好，可以写入：

```md
## 内容与方案输出偏好

- 输出业务方案时，优先给可落地的页面形态、关键词策略、转化路径和参考案例，避免只给泛泛方向。
```

---

## 反馈日志

每次成功写入 `AGENTS.md` 后，建议同步记录到：

```txt
.agents/feedback-log.md
```

日志格式：

```md
## YYYY-MM-DD

- 触发原因：[用户反馈的简要描述]
- 沉淀规则：[最终写入的规则]
- 写入位置：[AGENTS.md 路径和章节]
```

日志中不要记录隐私信息，不要完整复制用户原话，只记录抽象后的规则。

---

## 中文输出要求

使用本 Skill 时，所有面向用户的内容必须使用中文。

包括：

* 反馈总结
* 规则提炼
* 写入建议
* 确认问题
* 修改完成说明
* 冲突说明

除非用户明确要求英文，否则不要用英文回复。

---

## 标准回复模板

### 发现可沉淀反馈时

````md
我先暂停一下，先把这次反馈总结清楚，避免继续沿着错误方向做。

我理解这次反馈是：

- 我刚才的问题：[说明问题]
- 你真正想要的是：[说明用户意图]
- 这类问题是否适合沉淀：[是 / 否]

我建议把它沉淀成这条规则：

> [规则]

建议写入：

- 文件：[AGENTS.md 路径]
- 章节：[章节名]

拟写入内容：

```md
[Markdown 内容]
```
````

确认后我再写入。你可以回复「确认写入」「调整一下」或「不要写入」。

### 不适合沉淀时

```md
我理解这次反馈更像是当前任务的一次性调整，不建议写入 AGENTS.md，避免长期规则变得混乱。

我会在当前任务里按这个方向继续：

- [新的执行方向]
```

### 写入完成后

```md
已写入 AGENTS.md。

本次沉淀的规则是：

> [规则]

后续遇到类似情况，我会优先按这条规则执行。
```

---

## 核心原则

这个 Skill 的目标不是让 agent 随便自我修改，而是建立一个可控的反馈闭环：

用户否定 → agent 总结 → 提炼通用规则 → 用户确认 → 写入 AGENTS.md → 后续上下文持续改进。

任何时候都不能绕过用户确认。
