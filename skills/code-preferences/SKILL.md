# 代码偏好

这些规则适用于代码工作。遵循用户当前任务的明确要求；发现规则之间或规则与任务之间有冲突时，说明冲突并询问，不要自行忽略规则。始终用中文沟通、制定计划和反馈 Code Review。

## 动手前

- 先阅读相关源文件，说明关键假设和不确定点。若存在多种合理理解，列出选择；若有更简单的实现，说明原因。
- 提出简短实施计划及可验证的完成标准，并在修改前取得用户明确确认。
- 开始开发前询问沿用当前分支还是创建新分支。新分支命名为 `codex/` 加上与请求相符的简短英文词，最多五个词，以 `-` 连接。切换到 `codex/*` 分支前，先切到 `main` 或 `master`、拉取远端最新代码，再从更新后的基线创建或切换分支。

## 实现

写代码、改代码或做 Code Review 前，必须枚举并读取 [rules 目录](rules/) 下的每个 Markdown 文件，严格遵守其中所有适用规则。`SKILL.md` 不重复存放具体编码规则；规则之间或规则与当前任务有冲突时，向用户说明并确认取舍。不能因某条规则的例子与当前业务名称不同就跳过它。

## 验证与交付

- 按计划验证实际行为；修复缺陷时先复现问题，再确认修复有效。测试应覆盖有意义的行为，不写仅重复实现的测试。
- 提交前检查 changeset 并审查全部改动。提交信息遵循项目的 commitlint / config-conventional；创建提交或 PR 时加入署名尾注 `Codex <noreply@openai.com>`。
- 在终端或浏览器执行需要访问外部接口的命令前，检查 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 及对应小写变量；如存在，须在该命令中显式 unset 这些变量，使用直连。

## 增加规则

用户后续补充规则时，在 `rules/` 中为独立规则创建文件，或更新已有同义规则。每个文件按“标题、规则描述、不好的写法、喜欢的写法”组织，并说明适用范围。保留仍有效的旧规则；若新旧规则冲突，先向用户确认取舍。只增加能改变实际编码决策的规则。
